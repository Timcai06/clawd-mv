# pdoom-video 源码学习笔记：供 clawd-mv 与 Opus 参考

分析日期：2026-10-01。上游 HEAD：`bdbad537a7b7af3213475651774030c47568c181`；与 clawd-mv 的 `reference/pdoom/UPSTREAM_COMMIT` 一致。

证据范围：上游完整源码、规范、时间线与数据，及 clawd-mv 当前源码的静态比较。本次没有播放参考视频、运行参考渲染器或做视觉验收。以下区分代码事实、规范意图和迁移建议。

## 1. 核心判断

最值得学习的是三件事：每场围绕歌词设计自己的视觉机制；场景之间通过形状、位置和运动交接；底层渲染由歌曲时间驱动，让作者可以反复修改同一段并可靠导出。

上游当前有 17 个主场景模块、22 个时间线条目，歌词数据有 46 行、227 个词。17 个模块包含重复使用的 prompt 和 hook。22 是本次直接统计的数字，不沿用旧文档里的 23。条目数不等于镜头数：场景内部有重新构图、机位变化和阶段切换。

clawd-mv 已继承这个引擎。14 个上游引擎 TypeScript 文件中，9 个与当前项目逐字节相同：`scale.ts`、`audio.ts`、`lines.ts`、`stroke.ts`、`type.ts`、`scene.ts`、`gl.ts`、`util.ts`、`glsl/common.ts`。其余 5 个均存在；`engine.ts` 的差异是移除 P(doom) HUD 关联，核心采样逻辑保留。因此当前工作应着重使用已有能力和补足制作工具。

## 2. 一致性与变化分别由什么承担

规范意图：整片像一本关于末日的图解论著，各场采用雕刻、示波器、公文、蓝图、3D 空间、织物、界面等不同表达。统一来自色板、字体角色、颗粒、火花与线、反复出现的概率数值，以及冷幽默。

源码印证：`_motifs.ts` 集中提供火花和面具；各场使用自己的绘制代码并返回后期覆盖参数；`hook.ts` 通过 `params.n` 提供四种变体，`prompt.ts` 通过三个 variant 改变同一提示框的舞台和动作。

对 clawd-mv：我们的统一元素已经是 Clawd、光标、色板与字体。继续学习每场的组织方法，不必搬入上游的末日语义、面具或概率数值。

## 3. 最值得 Opus 细读的场景

| 源码 | 已观察到的实现机制 | 对我们有用的学习点 |
|---|---|---|
| `hook.ts` | 按词冲击；单独读取 DOOM 音节；四次副歌改变色场、尺度、节奏与退出方式 | S08/S13/S17 共用主题，但分别设计推进和收尾 |
| `loss.ts` | 火花绘制曲线；字沿曲线出现；曲线下落延续为 3D 地形；镜头跟随火花 | 把数据结构变成可穿行的世界，而不是仅换展示组件 |
| `stack.ts` | 歌词分配到 3D 栈块；逐拍下降、预备运动、弹簧落位；关键字附近骤停并改变块的姿态 | S14 的下降应有阶段和落点；文字与纵深共同表达 |
| `loom.ts` | 概率树写出词；MASK 按逐词进度揭开；画面通过 Droste 递归进入下一空间 | 为歌词建立场景专属机制；同一场可以包含几个语义阶段 |
| `prompt.ts` | 提示词逐词输入；候选概率出现；机位跟随光标、输入区域和按键；三段不同情绪 | S06/S09 的界面应围绕当前动作构图，保留机器文字的身份 |
| `dense.ts` 及辅助模块 | 排版压缩、安全框突破、GPU 网格、倾斜桌面等分阶段表达 | 画面变化由歌词含义决定；每个阶段需要焦点 |
| `outro.ts` | 重新调用 opening 场景；加载先前场景缩略图进行倒带；结束回到起始画面 | 若要做回环或回顾，需要维护由真实渲染产生的派生资产 |

这些是源码机制分析，不表示已经验证每个效果在屏幕上的质量。

## 4. 场景交接是具体的几何约定

`hook.ts` 明确记录后续场景的交接几何：

- 第一遍副歌把数字收缩成火花，再留下 room 接手的 P(DOOM) 形状与中心位置。
- 第二遍把色场合成一道眼睑接缝，交给 ascent。
- 第四遍的重复数字转成线，交给 loom 的织线与根节点。

源码中这些位置和尺寸是复制的常量，注释说明这样做是为了不修改其他代理拥有的文件。这证明作者有意识地协调两场，但复制也存在以后两边改动不同步的问题。

clawd-mv 的 S07→S08 已有类似实践：上场光标收束到屏幕中心，下场以匹配的位置和高度接手。应先盘点已有交接，再由 Opus 决定哪些其他相邻场景值得这样处理。

Codex 可辅助：按指定切点导出前后若干帧、制作短片与对照页；记录 Opus 给出的交接物、屏幕位置、尺寸和运动方向。是否衔接自然，由 tim 判断。

## 5. 同步有多个层次，不能合成一条规则

`timeline.ts` 的 `cut()` 实际取首词之前或附近的最近一拍（带容差），不是所有切点都吸附到小节第一拍。它的 `after()` 则寻找句末最近的 downbeat。`dense` 的一处容差额外调整，注释解释为避免切断上一词。

场景内部同时使用：逐词起止、音节起止、拍点、底鼓/军鼓脉冲和声音包络。例如 hook 把 P( 与 DOOM 分开，stack 则让空间下降按拍点推进。

对我们：COMMIT 的 MIT 按实际唱出的重音定位；世界的重复动作可以按逐拍网格；不能把所有动作都量化到同一个下拍。具体例外应由 Opus 明确，辅助工具负责显示其时间差和检查数据缺口。

## 6. 歌词是一种几何和动作材料

规范把 Archivo 分配给人声，Mono 分配给机器，少量衬线字分配给预言式语气。源码中的歌词有多种载体：曲线路径、3D 平面、MASK 块、令牌、全屏数字和冲击字。

重要实现细节：`type.ts` 使用静态字体实例，Archivo 宽度有 6 档、字重有 4 档；`F.archivo()` 选最近一档。因此规范里“宽度和字重动画”不能直接理解为浏览器连续插值可变字体轴。Opus 做歌词 v3 时，应意识到这套 API 的离散特性，选择适合的表现办法。

另一项可直接沿用的能力是 `layout()` / `glyphX()`。它们保持分字、分色、擦除绘制时的字偶间距；逐词变色不应重新用前半字符串的简单测宽来定位后半段。

## 7. 确定性为什么是生产能力

场景主要根据 t 计算画面，粒子也可以按出生编号、出生时刻、hash 速度和年龄直接算位置。`_motifs.ts` 的粒子实现不用逐帧积累历史；变速发射还支持按出生时刻取发射率。

收益：拖到任意时间、重复渲染、局部导出、多次子帧采样都可以使用同一个场景逻辑。

但引擎并非完全禁止状态模拟：`Scene.stateful`、`reset()`、`prerollMax` 明确支持状态场景。自适应采样遇到这样的场景会拒绝运行，需要固定采样。不能笼统声称所有场景天然支持所有导出模式。

Codex 可做的验证：同一时间从不同跳转顺序到达后的输出比较，以及指定场景的运行和资源排查。这是稳定性证据，不是审美评分。

## 8. 输出质量：采样、尺度、编码需要分开理解

`Engine.render()` 的自适应采样按 4→12→36→108→324 加入子帧，通过图像变化估计何时停止。场景可以用 `maxSamples` 限制上限；shoggoth 就设了 108，注释指出其噪声会让采样器继续追逐。

后期、HUD、颗粒不跟每个子帧一起无限重复；场景先在线性 HDR 中累积，再完成最终输出。文档还要求与帧绑定的随机跳动使用 `frameIdx(t)`，避免中心快门把两个随机状态混成重影。

实时播放器用单采样；正式导出可用自适应采样。二者共享场景和时序，但运动模糊与压缩结果不同，因此不能把浏览器播放说成正式成片的逐像素等价物。

4K 使用 1920×1080 逻辑坐标和更高物理分辨率，连同 Canvas、GPU 线条、着色器一起处理。自建字体图集或离屏贴图仍需作者考虑自身分辨率。

`render.ts` 把原始 RGBA 帧通过 WebSocket 送进 ffmpeg，并等待编码器确认以限制积压。编码显式采用 BT.709 矩阵与标签，避免生成与解码色彩矩阵不一致。关闭 HMR 是保护长时间导出的一项实际措施。

辅助任务：维护可比较的草稿/验收/正式参数；记录采样分布和每场耗时；保留机器/GPU/分辨率/快门条件。不要照搬作者机器上的耗时估计。

## 9. 音频分析不能当作一键通用服务

`analyze.py` 明确拟合恒定速度，并使用针对原曲的小节段落表。`align.py` 融合 CTC 输出、用 Whisper 交叉核对，再结合人声特征修正，有逐词人工 FIX。最终置信度是启发式评分；部分人工修正也保留低分，并不意味着所有时间戳都准确。

clawd-mv 已建立允许变速的逐拍数据。应继续使用本曲数据，不退回恒速拟合，也不复制原曲的手工时间和发音字典。新增人工修正应记录词、时间、依据和待听验状态；调试记录和模型缓存应能被找到，避免只有最终 JSON 可追溯。

## 10. 我建议承担的辅助任务顺序

| 顺序 | 任务 | 交付 | 设计决策的负责人 |
|---|---|---|---|
| 1 | 分镜图与实现同镜头对照 | 有场景/镜头/时间/版本的并排页；需要时增加同镜头多个阶段 | tim 指出差距，Opus 改画面 |
| 2 | 场景交接检查材料 | 切点前后帧组、短片、交接约定表 | Opus 设计，tim 验收 |
| 3 | 歌词同步辅助 | 词/音节/拍点时间表与待复核短片 | Opus 决定动作，tim 确认听感 |
| 4 | 导出与性能记录 | 采样分布、逐场耗时、日志、产物参数 | Opus/tim 决定效果与成本取舍 |
| 5 | 明确规格的工程修复 | 修复渲染统计、编码与资源问题，保留验证证据 | Codex 执行；涉及画面选择交回 Opus |
